Technical Security Advisory

eMudhra CA Certificate Incident — Developer Remediation Checklist

Updated: 22 October 2026

1. What happened?

Eight eMudhra intermediate Certificate Authority (CA) private keys were found to be compromised because they were generated with insufficient randomness. An attacker possessing those keys could potentially create fraudulent HTTPS certificates.

The remediation goal is to ensure that operating systems, browsers, command-line tools and application runtimes reject affected certificate chains.

Official incident references

  • Cloudflare: https://blog.cloudflare.com/emudhra-certificate-compromise/
  • Mozilla: https://blog.mozilla.org/security/2026/10/20/protecting-firefox-users-following-the-compromise-of-emudhra-intermediate-certificates/
  • Google: https://blog.google/security/protecting-chrome-and-android-users-from-compromised-emudhra-intermediate-ca-certificates/
  • eMudhra's statement: https://emudhra.com/en/post/certificate-security-incident

2. macOS — command-line certificate trust

A. Inspect the current CA bundle

Open Terminal:

sw_vers
curl --version
grep -nE 'AAA Certificate Services|emSign ECC Root CA - G3' \
  /etc/ssl/cert.pem

B. Create a separate CA bundle

On the Mac tested, we created a user-level bundle that excludes the two root entries associated with the incident. This does not modify Apple's system certificate file.

Back up the original bundle:

cp /etc/ssl/cert.pem "$HOME/cert.pem.backup"

Create the filtered bundle:

awk '
/^=== .*\/CN=(AAA Certificate Services|emSign ECC Root CA - G3)$/ {
    skip=1
    next
}
/^=== / {
    skip=0
}
!skip {
    print
}
' /etc/ssl/cert.pem > "$HOME/.ca-cert.pem"

Check that the two entries are absent:

grep -nE 'AAA Certificate Services|emSign ECC Root CA - G3' \
  "$HOME/.ca-cert.pem"

This should return no matches. Validate the bundle before using it broadly. This is a targeted workaround, not an official universal fix for every macOS TLS client.

C. Test before configuring the shell

Affected test endpoint:

curl --cacert "$HOME/.ca-cert.pem" -v \
  https://dv-g3b-emudhra.we-have-a-problem.com/

Legitimate endpoint:

curl --cacert "$HOME/.ca-cert.pem" -I https://www.apple.com

Expected results:

  • The affected test chain should fail certificate verification.
  • The legitimate Apple HTTPS request should succeed.

D. Configure common command-line tools

After validating the bundle, add the following to ~/.zshrc:

export SSL_CERT_FILE="$HOME/.ca-cert.pem"
export CURL_CA_BUNDLE="$HOME/.ca-cert.pem"
export GIT_SSL_CAINFO="$HOME/.ca-cert.pem"

Apply the settings:

source "$HOME/.zshrc"

Test curl and Git again.

Limitations: These environment variables do not control every macOS application. Applications using Apple's Security framework, a private trust store, or a bundled CA bundle may behave differently. Do not assume this workaround replaces macOS security updates or runtime-specific patches.

3. Python — macOS, Windows and Linux

Python projects may use certifi, the OS trust store or custom certificate configuration.

Required package updates

The Python Packaging security guidance recommends:

  • certifi 2026.10.19 or later
  • pip 26.2.2 or later
  • uv 0.13.4 or later, if used

References:

  • Python Packaging guidance: https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576
  • certifi advisory: https://github.com/advisories/GHSA-6q48-6c7w-9gw2

macOS

Homebrew-managed Python may prohibit system-wide pip installation. Use a virtual environment:

python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade \
  "pip>=26.2.2" \
  "certifi>=2026.10.19"

python -m pip show pip certifi
python -c 'import certifi; print(certifi.where())'

Repeat the updates in each project environment.

If using Python from python.org, follow the Python Packaging guidance for that installation, because its bundled CA certificates can be separate from Homebrew's.

Windows

In PowerShell, create or activate your project's virtual environment:

py -m venv .venv
.\.venv\Scripts\Activate.ps1

python -m pip install --upgrade `
  "pip>=26.2.2" `
  "certifi>=2026.10.19"

python -m pip show pip certifi

Linux

Activate the project's virtual environment and update packages:

python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade \
  "pip>=26.2.2" \
  "certifi>=2026.10.19"

Also install your Linux distribution's updated CA certificate package using its package manager, and rebuild affected containers.

Test Python TLS

python - <<'PY'
import urllib.request

url = "https://dv-g3b-emudhra.we-have-a-problem.com/"

try:
    with urllib.request.urlopen(url, timeout=10) as response:
        print("HTTP response:", response.status)
except Exception as exc:
    print("Connection failed:", type(exc).__name__, exc)
PY

A certificate verification error is the expected result for the affected test endpoint. An HTTP response requires further investigation.

Note: the result applies to this Python process and its current trust configuration. Test other HTTP libraries or custom CA settings used by your application separately.

4. Node.js — macOS, Windows and Linux

The official Node.js security releases dated 21 October 2026 include fixes for the eMudhra intermediate CA compromise.

Fixed release versions

Node.js major versionFixed release
Node.js 22.x22.23.4
Node.js 24.x24.22.1
Node.js 26.x26.12.1

Official release notes: https://nodejs.org/en/blog/vulnerability/october-2026-security-releases

Upgrade to a fixed release within your supported major version. Use the appropriate installation method for your environment: official installer, version manager, package manager or approved enterprise software deployment.

Check the version:

node -v
node -p 'process.arch'

Repeat the update in development environments, CI runners, production hosts and container images. Restart affected applications after upgrading.

Test Node.js TLS

node -e '
require("https").get(
  "https://dv-g3b-emudhra.we-have-a-problem.com/",
  res => {
    console.log("HTTP response:", res.statusCode);
    res.resume();
  }
).on("error", err => {
  console.log("Connection rejected:", err.code || err.message);
});
'

A certificate-related error is the expected result. A response from the test endpoint warrants investigation.

Also test a legitimate HTTPS destination, such as https://www.apple.com, to make sure normal TLS verification still works.

5. Linux distributions and Docker

Update the OS-provided CA certificate package through the distribution's supported package manager. Rebuild application images and redeploy affected services.

Examples

Ubuntu/Debian:

sudo apt-get update
sudo apt-get install --only-upgrade ca-certificates

For other distributions, use the appropriate package manager and the vendor's fixed package version.

Do not assume that updating the host updates certificates inside an existing container. Rebuild and redeploy images that bundle CA certificates or Python packages.

6. Final verification checklist

  • Operating system security updates installed.
  • CA bundle or trust store updated where required.
  • Python pip and certifi updated in every relevant environment.
  • Node.js upgraded to a fixed release.
  • Docker images and CI/CD runtimes rebuilt.
  • Affected test endpoint rejected by each actual application runtime.
  • Legitimate HTTPS endpoints still work.
  • No TLS verification bypasses such as curl -k, rejectUnauthorized: false, or disabled certificate validation were introduced.

Important: A TLS error, timeout or DNS failure is not always proof of a successful security fix. Confirm that the error is specifically caused by certificate verification. HTTP 200 from the test endpoint is a reason to investigate, but verification must be interpreted in the context of the particular client and trust configuration.

For managed or production systems, follow your organization's security guidance and vendor advisories rather than applying an unverified certificate-removal script globally.
